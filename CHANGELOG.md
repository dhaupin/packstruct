### Added

- **The `requires` relevance key and the skip-before-import lifecycle norm (SPEC v1.3.0).** One additive row: the host-owned manifest key `requires` (an array of kebab-case capability tokens a pack needs from its run root, e.g. `"requires": ["wordpress"]`) plus the lifecycle norm that gives it meaning. A conforming loader whose run root declares a non-empty `provides` MUST skip, before import, any pack whose `requires` is not a subset of `provides` (and any pack named in an explicit `ignore` deny-list, which wins); the skip is reportable, and a run root declaring neither is byte-identical to before. The mechanism is deliberately the honest inverse of a `.packignore` deny-list: it fails CLOSED (a newly shipped pack naming an unmet capability skips itself, with no per-run-root upkeep) and travels WITH the pack (a manifest field, so lint sees it). The vocabulary is host-owned and free-form - the spec never forks a shared capability list; `packstruct lint` shape-checks the tokens (kebab-case, non-empty, unique) and assigns them no meaning. `spec/SPEC.md` sections 2 (table + acknowledged keys), 4 (the norm), 8 (row 9), and 10 carry the row; a new `requires-claims` conformance case proves a conforming loader does not REFUSE a pack that declares the key (the `audit-conformance` bundle is now 10 cases, 3 accept); five new refusal-matrix rows pin the shape rules both ways (packstruct + crashtest agree on all five). Engine receipt: crashtest's loader `src/packs/relevance.js` (dhaupin/crashtest#104). No `schemaVersion` move; no change to a host that declares nothing.

- **Three audience tiers, and a plain-language front door.** The site now speaks to who is reading it, at three depths, all grounded in SPEC v1:
  - `/start` - the absolute-beginner on-ramp. What a pack is in plain words (a folder with a label file), a copy-paste first pack, the one command that checks it, and a table of the mistakes the linter catches by name. No prior knowledge assumed.
  - `/extend` - the hobbyist/builders path. Pick a profile (scenario / check), check it deeper with `--deep` (entry import + id census), prove a loader with `audit-conformance`, add a new host (the "traveler" on-ramp, SPEC section 10), and the four house rules.
  - `/enterprise` - the fleet path. What enterprise needs (frozen and versioned, provable conformance, exact-pin receipts, governance as packs), a four-step adoption path, the MIT/OSS posture, and prefilled issue forms.
- **Prefilled GitHub issue links, built in the browser.** A tiny pure module (`web/src/issues.js`) builds `github.com/dhaupin/packstruct/issues/new` URLs with the right template, title, and a short body - opened in a new tab for the human to review and submit. Nothing is POSTed from the site; the visitor is the only one who can create the issue. The same pattern vant's contact composer uses.
- **GitHub issue templates and a template chooser.** `bug_report.md`, `feature_request.md`, `adoption.md`, and `new_host.md`, plus `.github/ISSUE_TEMPLATE/config.yml` (blank issues off; contact links to Discussions, SPEC v1, and the fleet page). Two new labels, `adoption` and `host`, carry the new forms. The web forms deep-link these templates by name.
- **A CONTRIBUTING.md front door.** The short path in (the five forms, the branch flow), the gate to run (`npm test && npm run check`), the two rules that surprise first-timers (a new check ships with a fixture that breaks it; pins, never floats), and pointers to AGENTS.md as the canonical source.
- **Two memstruct-bound entry profiles: `memory` and `sync` (SPEC v1.2.0).** packstruct now declares four profiles, not two. `memory` (default export `{ records: [Record] }`) is vant's markdown store; `sync` (default export `{ merge(local, remote) }`) is gistory's pure merge. Both bind the host-owned [memstruct](https://github.com/dhaupin/memstruct) standard - the record grammar and the four-property merge contract - by LINKING to it, the same one-address rule the `scenario` profile applies to crashtest's contract. Separation of concerns: packstruct owns the pack (manifest + entry + lifecycle), memstruct owns the record grammar and the merge contract, and the two profiles are where they meet. Canonical pages: `profiles/memory.md` and `profiles/sync.md`; the SPEC §3 rows and §8 v1.2.0 rows carry the receipts (vant's store, gistory's merge). A sync pack is graded by `memstruct audit-merge`, not by any packstruct lane. No `schemaVersion` move, no manifest field added.
- **The `staging-ff-sync` workflow (the family staging flow).** packstruct promotes by merge commit, which by design leaves a commit on `main` that `staging` lacks - so the two drift on every promote even when the flow is followed exactly. The required sync step is a fast-forward of `staging` back to `main`, and every repo that promotes by merge commit carries `.github/workflows/staging-ff-sync.yml` (monoforge, gistory, coreforge, memstruct, gamestruct) except this one. Vendored verbatim from the canon (no `uses:` steps, so no Action pins). Non-destructive by construction: a fast-forward-only refspec, so a real divergence fails the job loudly instead of rewriting history. Receipt: the 3-commit drift left by PR #88's promotion (`e502808` + `c215820`) was fast-forwarded by hand (`staging` -> `c215820`, `force:false`), then this workflow kept `main == staging` on the next promote (`b1e22f6`).

## [1.1.0] - 2026-10-29

### The docs-lane consolidation (2026-11-04)

The family built docs from four topologies; the two reusable lanes had drifted (ruby 3.2 vs 3.4, pagefind `latest` scrape vs npm pin). The docs lane is now ONE canonical reusable workflow in `dhaupin/freestruct`, and this repo is a thin caller of it.

- `.github/workflows/docs.yml` calls `dhaupin/freestruct/.github/workflows/docs-lane.yml@22bb7e9b2634d6cdd966963d9e25c7f892577276`, keeping only the trigger, permissions, concurrency, and this repo pins.
- No `package-lock.json` here (a library), so the lane installs with `npm install` and skips the npm cache; no `crashtest.config.js`, so the dogfood leg is off.
- No version bump; a workflow consolidation, not a released surface.

### Security

- **Every GitHub Action ref is now SHA-pinned ("pins, never floats").** `publish.yml` already pinned; `docs.yml`, `corpus.yml`, `crashtest.yml`, and `test.yml` floated 13 refs (`actions/checkout@v4`, `actions/setup-node@v4`, `ruby/setup-ruby@v1`, `actions/configure-pages@v4`, `actions/upload-pages-artifact@v5`, `actions/deploy-pages@v4`). All 13 now name the family canon commit SHA (tag kept in the trailing comment). A new guard, `scripts/check-action-pins.cjs`, refuses any non-SHA `uses:` ref and runs as `npm run lint:pins` inside `npm run check`, so a future float fails in CI instead of drifting in silently.

### Fixed

- **`runCapped` now honors `maxBuffer` on stderr, and truncates any chunk that straddles the cap.** The stderr data handler lacked the `capped` guard the stdout handler carried, and neither stream truncated an oversized chunk - so a loader flooding stderr returned output PAST `maxBuffer` (a single 1 MiB chunk against a 4 KiB cap returned ~146 KiB), the exact unaccounted bytes the honesty cap exists to refuse. Both streams now share one `absorb` that truncates to the remaining budget and kills the child; `test/run-capped.test.mjs` pins the cap on both streams and the combined budget.

- **The release ladder no longer parses `npm pack --dry-run --json`.** The phone's npm answers that probe with empty stdout (a config warning, no JSON) even under `--loglevel=error`, so the ladder's `JSON.parse` failed and read as a capability failure - exit 2 - on a clean tree. The ladder now derives the expected set from a REAL `npm pack` of the checkout, listed by the same `tarList` the served tarball already goes through.

- **The staged publish `.npmrc` no longer writes the deprecated `always-auth` line.** npm >=9 warns `Unknown project config "always-auth"` on it, and that warning reaches the child processes the `prepublishOnly` gate spawns. The staged file is now exactly one line (the `${NPM_TOKEN}` expansion).

### Changed

- **Changelog + release-notes standardized to the family shape.** `CHANGELOG.md` is now Keep-a-Changelog end to end (a `## [Unreleased]` block over `## [version] - date` sections) and `scripts/release-notes.cjs` is the family's single superset extractor: it reads the KAC heading, still reads the older bare (`## 1.2.0`) and v-prefixed (`## v1.2.0`) forms, closes the version token so `## [1.2.0]` never matches a `## [1.2.0-rc.1]`, and refuses a version with no section by name. One extractor across the family means one release-body shape everywhere.

### Fixed

- **The release ladder no longer races registry propagation, nor false-flags a branch-name `target_commitish`** - both surfaced by the crashtest 1.2.0 live cut. `scripts/verify-release.cjs` polls `dist-tags.latest` **and** the version entry through npm's post-publish propagation window instead of reading once (the first read saw the old `latest`), and the `release` job retries `npm pack <pkg>@<ver>` the same way (it read `ETARGET: no matching version` seconds after publish). The release check now accepts GitHub's `target_commitish` default-branch name and treats only a 40-hex SHA as a commit claim (a branch name is not drift; the tag is the identity). Two pins in the release-verify leg hold both fixes.

### Fixed
- **The `entry` check was a substring proxy, not a containment test (packstruct#2).** `entry.includes('..')` both over- and under-refused: (a) it PASSED an absolute path like `entry: "/index.js"` - node's `join` re-roots it inside the pack, so the shallow pass said clean while the deep probe's `resolve` treated it as `/index.js` and refused: the same manifest drew two verdicts, and SPEC §2 says entry MUST be a relative path inside the pack dir; (b) it FALSE-REFUSED a legitimate in-pack filename like `a..b.js`. Both checks now share one real containment test (`entryEscape`): reject non-strings, NUL, and absolute paths (POSIX or Windows-drive), then resolve against the pack dir and require the result to stay under it. `armedCoverage` uses the same test (it carried the same substring bug). The dogfood's `entry-path-containment` case grew two shapes (`entry-absolute-inpack`, `entry-dot`) - the old absolute shape (`/etc/passwd`) also failed file existence, which masked the bug.
- **A symlink entry escaping the pack passed both passes clean.** The containment test above is lexical, so `entry: "index.js"` where `index.js` is a symlink to a valid module OUTSIDE the pack was accepted silently on the shallow pass AND imported on the deep pass - no refusal, code loaded from outside the pack. "Inside the pack dir" is now PHYSICAL: the entry is realpath'd and must resolve under the realpath'd pack dir (both sides realpath'd, so a symlinked ancestor of `packDir` itself does not false-refuse). An in-pack symlink stays clean. `armedCoverage` gets the same physical check. SPEC §2 now says containment is physical, not merely lexical. New unit cases (escape refuses both passes; in-pack link stays clean) + dogfood shape `entry-symlink-escape` (7 → 8 entry-escape shapes).
- **SPEC §7 under-described the linter's own surface.** §7 named only the shallow pass, while `packstruct lint --deep` (+ `--against`) emits norms (`entry-import`, `entry-default-export`, `id-duplicate`, `id-collision`, `id-library-collision`) that the SPEC never listed under Conformance tooling. They were already promised by §3/§4/§5, but §7 - the section that describes the tool - did not say so. §7 now documents the deep pass and names those refusals as the spec's own load-time refusals surfaced early, never new norms (the "never ship a check the SPEC doesn't promise" law, applied to the tool surface).
- **The linter shipped an `armed-coverage` refusal the SPEC never promised (packstruct#27).** `src/lint.mjs` refused a declared `armedCoverage` whose file did not ship, but `spec/SPEC.md` never listed the key - the exact "never ship a check the SPEC doesn't promise" defect (AGENTS.md). The SPEC now documents `armedCoverage` as a v1.1.0 lint-assist key (§2 + §8 row 6, explicitly NOT a shared fact no loader reads), so the refusal is promised.
- **The refusal matrix could go stale green (packstruct#3).** Two defects in `scripts/gen-refusal-matrix.mjs`, both against the repo's own law ("never ship a check the SPEC doesn't promise"): (1) the honesty check was a SUBSET compare, so a linter that grew STRICTER than the SPEC - an extra norm on a shape the SPEC says is fine - recorded `honest: true` and rewrote the matrix green; it is now an exact both-directions set compare. (2) CI ran the generator (which rewrites the file) but never DIFFED it against the committed receipt, so a flipped row shipped stale and silent; `--check` now regenerates in memory and exits 1 on any delta, covering the matrix and every `labs/refusal-battery/` file, and runs as a leg of `npm run check` (the `prepublishOnly` gate) plus the test workflow. `--check` also holds the golden set's packstruct column (`labs/refusal-matrix.golden.json`) against the linter, so a hand-edited or stale copy of the same observations cannot contradict the matrix it cites. `test/refusal-matrix.test.mjs` pins all five cases (in-sync passes; superset norm, stale matrix, tampered battery file, drifted golden column each fail).
- **The dogfood receipt was cut by the wrong crashtest (packstruct#29).** The committed `labs/crashledger.json` + `labs/hardening.md` were cut by crashtest **v1.0.0** (34 findings), but the README registry row attributed "34/34 REFUSED" to `crashtest@1.1.0` @ `2d1fe79` - the pin the workflow and the corpus lane already use. Re-ran the dogfood on v1.1.0: 53/53 catalog findings REFUSED (4 from `packstruct-lint-shapes`), 0 EXPLOITED, 0 BOUNDED, and the registry row now matches the committed ledger it cites.

### Fixed
- **`runCapped` group kill (QC leak pass, the CI-kill cause found): caps now SIGKILL the whole process group, not just the direct child.** Loaders spawn under `shell: true`, so when `/bin/sh` forked instead of exec'ing, a cap-killed flood loader left an orphaned node grandchild holding the stdout pipe: with nobody reading, `console.log` buffers every write in the child's own memory, gigabytes per child in seconds. Four leaked children from one suite run ballooned a dev sandbox 104MB -> 3.3GB used and starved CI runners mid-suite - the publish lane's five `exit 143` job deaths all landed inside the probe-heavy phases where those children are alive. The child now spawns detached (own process group) and every kill path - deadline and cap, stdout and stderr - signals the negated pid, taking the shell and every grandchild in one shot. Verified empirically: suite PASS with zero surviving children and flat memory where the leak measured 3.2GB.
- **`lint --deep` probe isolation (QC vuln pass): pack code can no longer drive the linter's own process.** Entries were imported in-process, so pack.json cargo with top-level code could hijack the CLI's exit code (`process.exit(7)` in an entry made `packstruct lint --deep` wire-exit 7 with zero output) or hang it forever (`for(;;){}` at top level). Probes now run in a disposable child with a 5s SIGKILL timeout; both crash classes became honest `entry-import` refusals naming the entry and the reason. Fixtures both ways (`test/fixtures/edge/exit|spin`), wire-level asserts: exit stays 1 - the CLI's own contract, never the entry's.
- **`audit-conformance` loader caps (QC vuln pass):** a HOST loader is arbitrary code in the shell it owns, but a refusal is instant - a loader that hangs is killed at the 120s audit timeout (neither accept nor refuse), and output above the 1MB spawn buffer counts as no-verdict. Both surface as audit violations naming the case; loaders can no longer surprise the harness with a hang or an output flood. Tests both ways.
